# ShopVerse observability

Everything here is deployed by ArgoCD: the tools are Applications in
`gitops/envs/<env>/apps/platform.yaml`, and the content in this directory (dashboards, rules,
Alertmanager template) is pulled into every environment by `gitops/envs/<env>/platform/kustomization.yaml`.

## Signals -> tools

| Signal | Producer | Transport / collector | Store | UI | Retention |
|---|---|---|---|---|---|
| **Metrics** (RED) | each service `GET /metrics` (prom-client: `http_request_duration_seconds{method,route,status}`, Node.js runtime, `orders_created_total`, `saga_completed_total{result}`) | ServiceMonitor `<svc>` (via headless `<svc>-metrics`, so canary pods are scraped too) | Prometheus (kube-prometheus-stack, gp3 PVC) | Grafana `grafana.<env domain>` | dev 3d, staging 7d, prod 15d |
| Metrics (platform) | node-exporter, kube-state-metrics, ingress-nginx, Karpenter, KEDA, ESO, Argo Rollouts, Velero, kafka-exporter, postgres/redis exporters (dev), blackbox probes | ServiceMonitor / PodMonitor / Probe | Prometheus | Grafana | same |
| Metrics (AWS managed) | RDS, ElastiCache, MSK, ALB | CloudWatch | CloudWatch | Grafana CloudWatch datasource (IRSA `shopverse-<env>-grafana`) | CloudWatch default |
| Metrics (from traces) | spans | OTel Collector `spanmetrics` connector -> Prometheus exporter `:8889` | Prometheus (`traces_spanmetrics_*`) | Grafana | same |
| **Logs** | services (pino JSON on stdout: `level`, `msg`, `service`, `trace_id`, `span_id`, `correlationId`), ingress-nginx JSON access log (`trace_id`) | Fluent Bit DaemonSet (`logging`) -> kubernetes metadata -> JSON lift | Elasticsearch (ECK, `logs-k8s-*` daily indices) | Kibana `kibana.<env domain>`, Grafana Explore (`Elasticsearch-logs`) | ILM: dev 7d, staging 14d, prod 30d |
| **Traces** | services (OTel Node SDK, OTLP/HTTP to `http://otel-collector.tracing:4318`), ingress-nginx (OTLP/gRPC 4317, root span) | OpenTelemetry Collector (`tracing`, k8sattributes) | Jaeger collector -> Elasticsearch (`shopverse-jaeger-*`) | Jaeger `jaeger.<env domain>` (basic auth), Grafana Explore (`Jaeger`) | es-index-cleaner: dev 7d, staging 14d, prod 30d |
| **Alerts** | PrometheusRules (chart per service + `prometheus-rules/`) | Prometheus -> Alertmanager | - | Slack + email (critical) | - |
| Cost | Kubecost (reads the same Prometheus) | - | Kubecost PV | `kubectl -n kubecost port-forward svc/kubecost-cost-analyzer 9090` | - |

## Correlating a request end to end (trace_id)

1. ingress-nginx starts (or continues, `opentelemetry-trust-incoming-span`) a trace and writes the
   W3C `traceparent` header upstream; its JSON access log contains `trace_id`.
2. The service's OTel SDK continues the trace; the pino logger mixin writes the active `trace_id` /
   `span_id` into every log line; Kafka producers inject `traceparent` into message headers, so
   consumers (inventory, payment, ...) continue the same trace across the saga. The CloudEvents
   envelope also carries `correlationId` (= sagaId = orderId).
3. Prometheus histograms carry exemplars (`trace_id`) - the "p95 latency by service" panel in
   *ShopVerse / Service RED overview* links a slow bucket straight to Jaeger.
4. In Jaeger, *Logs for this span* (Grafana `tracesToLogsV2`) queries Elasticsearch with
   `trace_id:"<id>"`; in Kibana/Grafana logs, the `trace_id` field is a data link to Jaeger.
5. For a business-level view of one order, search Kibana for `correlationId:"<orderId>"` - this
   returns every service's lines for that saga even across separate traces (e.g. saga timeout job).

Typical incident flow: alert (Slack, with runbook + dashboard links) -> RED dashboard (which service,
which route, since which deploy annotation) -> exemplar -> Jaeger trace (which hop is slow/failing) ->
logs for that `trace_id` (the actual error) -> rollback/abort if a deploy caused it (`docs/runbooks/rollback.md`).

## Layout

| Path | Content |
|---|---|
| `grafana-dashboards/*.json` | `service-red-overview` (per service RED + saturation + canary vs stable), `order-saga-funnel` (orders_created vs saga_completed{result}), `kafka-consumer-lag` (lag, DLQ inflow, KEDA), `cluster-capacity` (requests vs allocatable, pressure, spot/on-demand, Karpenter), `rds-cloudwatch` (RDS via CloudWatch). Loaded by the Grafana sidecar from ConfigMaps labelled `grafana_dashboard=1` (generated by `kustomization.yaml`). |
| `prometheus-rules/` | `slo-availability` (99.9% SLO recording rules + multi-window burn-rate alerts), `kafka` (lag, growth, DLQ), `nodes` (pressure, NotReady, pending pods, Karpenter limits), `pods` (CrashLoopBackOff, OOMKilled, image pull, HPA maxed, Rollout degraded, ESO sync), `certificates` (TLS expiry + endpoint probes via blackbox-exporter). |
| `alertmanager/` | `alertmanager.yaml.tmpl` (rendered by ESO with Slack/SMTP secrets from `shopverse/<env>/monitoring/alertmanager`), `shopverse.tmpl` (Slack/email message templates). |
| `fluent-bit/` | `parsers.conf` (pino, ISO JSON, nginx JSON, klog) - mirrored in the fluent-bit Application values. |

Per-service alerts (high 5xx ratio, p95 latency, restarts, no ready pods) are rendered by
`charts/microservice/templates/prometheusrule.yaml` so every new service gets them automatically.

## Service-side requirements

- Expose `http_request_duration_seconds` (histogram, seconds) with labels `method`, `route`
  (templated route, never the raw URL), `status`. Enable exemplars with the active trace id.
- Log JSON to stdout with `trace_id`, `span_id`, `correlationId`, `service`.
- Export traces with OTLP/HTTP to `OTEL_EXPORTER_OTLP_ENDPOINT` (set by the chart), propagate
  W3C trace context over HTTP and Kafka headers.
- order-service: `orders_created_total`, `saga_completed_total{result="confirmed|cancelled|timed_out"}`.
