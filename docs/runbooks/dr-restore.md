# Disaster recovery and restore

| Target | prod | staging | dev |
|---|---|---|---|
| **RTO** (service restored) | **1 hour** | 4 hours | best effort (rebuilt nightly anyway) |
| **RPO** (max data loss) | **15 minutes** | 24 hours | none guaranteed |

How the RPO is met in prod:

| Data | Mechanism | Achieved RPO |
|---|---|---|
| Orders, payments, users ... (RDS PostgreSQL, Multi-AZ) | automated backups + PITR (transaction logs shipped every 5 min), 14-day retention, daily snapshot copied to a second region by AWS Backup | <= 5 min |
| Redis (ElastiCache) | cache / refresh tokens / carts; daily snapshot, rebuildable | 24 h (acceptable: users re-login, carts are re-buildable) |
| Kafka (MSK, RF 3, min ISR 2, 3 AZs) | replication across AZs; topics are transient - the source of truth is Postgres + outbox | 0 within region; outbox re-publishes unsent events |
| Kubernetes objects + PVs | Velero `hourly-shop` (48h) + `daily-full` (30d) to `s3://shopverse-prod-velero`, EBS snapshots | 1 h (and Git is the real source: ArgoCD re-creates everything) |
| Media / audit archive | S3 versioning (+ replication if enabled in Terraform) | 0 |

> Git + ArgoCD is the primary recovery path for everything in the cluster. Velero is the safety net
> for things not in Git (PVCs, in-cluster secrets generated by ESO, Elasticsearch data).

## 0. Declare and coordinate (5 min)

1. Open an incident (see `incident-response.md`), name an Incident Commander and a scribe.
2. Decide the scenario: **A** single service data corruption, **B** cluster lost, **C** RDS lost/corrupted,
   **D** MSK lost, **E** full region outage.
3. Freeze deploys: `argocd proj windows add shopverse --kind deny --schedule "* * * * *" --duration 4h --applications "*"`
   (or pause the promote workflow).

## A. Restore Kubernetes state with Velero (cluster healthy, objects deleted/corrupted)

```bash
velero backup get --selector shopverse.io/backup-type=hourly-shop        # pick the last good one
velero restore create shop-$(date +%s) --from-backup <backup> \
  --include-namespaces shop --existing-resource-policy=update
velero restore describe shop-<ts> --details
```
Then let ArgoCD re-converge: `argocd app sync -l app.kubernetes.io/part-of=shopverse`.

## B. Cluster lost (re-create in the same region) - target 45 min

1. Terraform: `terraform -chdir=terraform/envs/prod apply` (VPC, RDS, MSK, ElastiCache survive - only EKS + node groups are re-created). ~15-20 min.
2. Bootstrap ArgoCD (Terraform helm_release) and apply the root app:
   `kubectl apply -n argocd -f gitops/bootstrap/prod-root.yaml`.
3. Waves re-create platform -> services (~15 min). Watch: `argocd app list`, `kubectl get pods -A | grep -v Running`.
4. Restore what is not in Git (Elasticsearch PVCs, generated secrets) from the last `daily-full`:
   ```bash
   velero restore create full-$(date +%s) --from-backup <daily-full-backup> \
     --include-namespaces logging,monitoring,tracing --existing-resource-policy=none
   ```
   Restoring generated secrets keeps Grafana admin / ES users stable; otherwise new ones are generated.
5. ExternalDNS re-points `api.ganga888.in` & tools to the new ALB (TTL 60s). Check:
   `dig +short api.ganga888.in` and the blackbox `probe_success` panel.

## C. RDS restore (point in time) - target 40 min

Use when data was corrupted (bad migration, accidental delete) or the instance is lost.

```bash
# 1. find the last good timestamp (from logs/audit-service), e.g. 2026-10-03T08:55:00Z
aws rds describe-db-instance-automated-backups --db-instance-identifier shopverse-prod-postgres   # Terraform output rds_instance_id
# 2. restore to a NEW instance (never in-place)
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier shopverse-prod-postgres \
  --target-db-instance-identifier shopverse-prod-postgres-pitr \
  --restore-time 2026-10-03T08:55:00Z \
  --db-subnet-group-name shopverse-prod-db --vpc-security-group-ids <rds-sg> \
  --multi-az --db-instance-class db.r6g.large --tags Key=Project,Value=shopverse Key=Environment,Value=prod
aws rds wait db-instance-available --db-instance-identifier shopverse-prod-postgres-pitr
```
3. Single-service corruption: `pg_dump` only that database from the PITR instance and restore it into
   the live instance (scale that service to 0 first: `kubectl -n shop scale deploy/<svc> --replicas=0`
   and pause its ScaledObject: `kubectl -n shop annotate scaledobject <svc> autoscaling.keda.sh/paused-replicas=0`).
4. Whole-instance loss: point the services at the new instance - update `host` in each
   `shopverse/prod/rds/<service>` secret (Terraform `rds_endpoint` variable, then apply), then force ESO refresh:
   `kubectl -n shop annotate externalsecret -l app.kubernetes.io/part-of=shopverse force-sync=$(date +%s) --overwrite`.
   The checksum annotation does not change for host-only updates, so restart:
   `kubectl -n shop rollout restart deploy` and `kubectl argo rollouts -n shop restart <rollout>` for order/payment/catalog.
5. Rename/promote in Terraform afterwards (import the new instance) so state matches reality.

## D. MSK recovery

- Broker loss: MSK replaces brokers automatically (RF 3, min ISR 2) - no action, watch `KafkaConsumerLagHigh`.
- Cluster lost / topics deleted:
  1. `terraform apply` re-creates the cluster and topics (6 partitions, RF 3, `<topic>.dlq`).
  2. Update `KAFKA_BROKERS` (Terraform output `msk_bootstrap_brokers_tls`) in
     `gitops/envs/prod/services/*/values.yaml` and the kafka-exporter app; merge -> ArgoCD rolls services.
  3. Consumers start at `earliest` (empty topics). Producers re-send everything still in the
     transactional outbox (`outbox` table rows with `published_at IS NULL`).
  4. Sagas stuck in `PENDING`/`STOCK_RESERVED` older than 5 min are compensated by the saga timeout
     job; verify on the *Order saga funnel* dashboard (timed_out spike, then flat).
  5. Idempotent consumers (`processed_events`) make any replays safe.

## E. Region outage (ap-south-1)

Not active-active. Recovery = scenario B + C in the DR region from cross-region snapshot copies
(AWS Backup) and the Velero bucket replica. Expected RTO ~4 h; requires running Terraform with the
DR region variables and moving Route 53 records. Decision owner: Head of Engineering.

## Validation checklist (all scenarios)

- [ ] `argocd app list` all Synced/Healthy
- [ ] Blackbox probes green (`probe_success == 1`) for web, api and tools
- [ ] Place a test order in prod with the synthetic test account; `saga_completed_total{result="confirmed"}` increments
- [ ] Kafka lag back to baseline, DLQ inflow 0
- [ ] Error budget burn alerts resolved
- [ ] Record actual RTO/RPO in the incident doc

## Quarterly DR drill (staging, then prod read-only parts)

| # | Drill | Pass criteria |
|---|---|---|
| 1 | Velero: restore `hourly-shop` into a scratch namespace `shop-drill` (`--namespace-mappings shop:shop-drill`) | all objects restored, pods Ready (images signed, secrets synced) |
| 2 | RDS PITR of prod to `-drill` instance, run `SELECT count(*)` checks per service DB, delete instance | restore < 30 min, data <= 5 min old |
| 3 | Staging cluster destroy + recreate from Terraform + root app | platform + services healthy < 45 min |
| 4 | MSK: delete and recreate a staging topic, verify outbox replay + idempotency | no duplicate orders/payments |
| 5 | Restore Elasticsearch PVC from a `daily-full` snapshot in staging | Kibana shows yesterday's logs |
| 6 | Review: backups encrypted, retention correct (30d/48h), `VeleroBackupFailed` alert fired in test | all yes |

Record results in the DR log (date, scenario, measured RTO/RPO, gaps, owners for follow-ups).
