ShopVerse: a 15-service e-commerce platform on AWS

ShopVerse is an online store split into 15 independently deployed microservices running on Amazon EKS. Customers reach it at ganga888.in through CloudFront and an Application Load Balancer. Orders run as a saga across order, inventory and payment over Kafka. Every change to code or infrastructure reaches AWS through Git: Jenkins and GitHub Actions build and plan, and ArgoCD and Terraform apply.

How a request flows

This is the path of a customer placing an order on ganga888.in. Each hop maps to a box in the diagram.

  1. Route 53 resolves ganga888.in to CloudFront and api.ganga888.in to the ALB (alias records that ExternalDNS keeps up to date).
  2. CloudFront serves the single-page web app from the private S3 web bucket. Its global WAF drops SQL injection, XSS, known-bad IPs and floods before they reach AWS in Mumbai. Calls to /api/* are forwarded to the ALB.
  3. The ALB terminates TLS with an ACM certificate, applies the regional WAF and forwards to the ingress-nginx pods. It was created by the AWS Load Balancer Controller from a Kubernetes Ingress, so nobody clicks it together in the console.
  4. ingress-nginx routes /api/v1/orders to order-service, applies per-client rate limits and adds request IDs.
  5. order-service verifies the customer's JWT against the auth-service public key (JWKS). In a single Postgres transaction it saves the order as PENDING and writes the saga commands to an outbox table.
  6. The outbox relay publishes ReserveStock to MSK. inventory, then payment, answer through Kafka. The order becomes CONFIRMED, or CANCELLED with compensation.
  7. Every hop emits a trace (OpenTelemetry to Jaeger), metrics (Prometheus) and a JSON log line with the same trace_id (Fluent Bit to Elasticsearch), so one slow checkout can be followed across all six services.

The 15 microservices

All services are Node.js 22 with TypeScript and Fastify. They share one internal library for logging, metrics, tracing, Kafka and health checks. Each service owns its data: one Postgres database per service on a shared RDS instance, separate Redis key prefixes, and no service reads another's tables.

What I added beyond your list

These fill gaps that would otherwise surface in production.

AWS Load Balancer Controller + ExternalDNS

Without them, the ALB and DNS records are built by hand and drift from the cluster. With them, an Ingress is the only thing you write.

OpenTelemetry Collector

One pipe for traces. Services stay vendor-neutral, and span metrics feed Prometheus.

Transactional outbox + idempotent consumers

A saga without these loses or duplicates events whenever a pod restarts mid-write.

Dead-letter topics

A poison message goes to <topic>.dlq after retries instead of blocking the partition.

VPC endpoints

ECR, S3, STS and Secrets Manager traffic stays private and skips NAT data charges.

Kyverno + cosign + SBOM

Closes the supply chain: only images that Jenkins scanned and signed can start.

KMS, CloudTrail, GuardDuty, Security Hub

Encryption you control, plus the audit trail and threat detection a real account needs.

AWS Backup with cross-region copy

Database backups survive the loss of the whole region or the RDS instance.

Strimzi and in-cluster data for dev

Dev runs Kafka, Postgres and Redis as pods (use_managed_data = false), which removes most of the managed-data cost while learning.

Nightly dev destroy and morning recreate

Scheduled GitHub Actions jobs. ArgoCD restores every app from Git when the cluster comes back.

SLO burn-rate alerts

Page when the 99.9% availability budget is burning fast, rather than on every CPU spike.

Runbooks

DR restore, incident response, rollback, secret rotation, scaling, promotion, and onboarding a new service.

CI/CD, GitOps and Terraform

Two pipelines are kept separate on purpose. Jenkins owns application builds and never has rights to change infrastructure. Its EC2 instance role can only push to ECR and sign with the KMS key, so no access key exists to leak. GitHub Actions owns Terraform through two OIDC roles: a read-only role for plans on pull requests, and an apply role usable only from main. Prod apply also waits for a human approval in the GitHub prod environment.

Order saga

Orchestration was chosen over choreography because the checkout flow has clear ordering and compensations. Keeping them in one state machine (PENDING → STOCK_RESERVED → CONFIRMED | CANCELLED) makes them testable and visible on one Grafana panel. A sweeper cancels any saga stuck for more than 5 minutes and runs its compensation.

Resilience and disaster recovery

  • Inside a zone: liveness, readiness and startup probes. PodDisruptionBudgets keep at least 2 prod replicas during node drains. Circuit breakers (opossum) protect every outbound call.
  • Losing a zone: pods spread across 3 AZs, RDS and Redis fail over automatically, and MSK replicates every partition 3 ways.
  • Losing the cluster: recreate it with Terraform. ArgoCD redeploys from Git and Velero restores anything not in Git.
  • Losing data: RDS point-in-time restore (RPO about 5 minutes), plus AWS Backup copies in a second region.
  • Targets for prod: RTO 1 hour, RPO 15 minutes. The Ansible restore-drill playbook proves this every quarter, and docs/runbooks/dr-restore.md lists the steps.

Build order: from empty account to live site

  1. Bootstrap state. terraform/bootstrap creates the S3 state bucket and lock table, once, with your admin credentials.
  2. Global resources. terraform/global creates the Route 53 zone, ECR repos, GitHub OIDC roles, KMS keys, CloudTrail, GuardDuty and budgets. Then set your registrar's nameservers for ganga888.in to the four NS values it prints.
  3. Dev environment. Open a PR on terraform/envs/dev, read the plan in the PR comment, and merge. GitHub Actions applies it.
  4. Bootstrap ArgoCD. The morning workflow installs ArgoCD and applies gitops/bootstrap/dev-root.yaml (or run those two steps by hand). Everything else (ingress, monitoring, logging, the 15 services) syncs from Git.
  5. Start Jenkins on EC2. Set admin_cidrs and apply terraform/ci, put the GitHub token in the shopverse/ci/jenkins secret, then run ansible-playbook -i inventories/ci/hosts.yml playbooks/jenkins.yml. Open https://jenkins.ganga888.in; the first build pushes all 15 images and bumps the dev tags.
  6. Verify. Run the Newman suite against api.dev.ganga888.in, then k6 load while watching HPA and Karpenter in Grafana.
  7. Promote. Apply staging and prod the same way, then promote image tags with the promote workflow. Prod applies and promotions wait for your approval.
